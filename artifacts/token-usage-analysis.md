# 上下文压缩对于Agent应用的影响

## 指标对比  
| 指标 | 带压缩 | 无压缩 baseline |
|---|---:|---:|
| 行动请求次数（ReAct steps） | 17 | 24 |
| 压缩请求次数 | 4 | 0 |
| **总 LLM 请求次数** | **21** | **24** |
| 行动请求累计输入 token | 72,713 | 222,550 |
| 行动请求累计输出 token | 3,101 | 5,028 |
| 压缩请求输入 + 输出 token | 21,999 | 0 |
| **全部请求累计输入 token** | **91,895** | **222,550** |
| **全部请求累计输出 token** | **5,918** | **5,028** |
| **全部请求总 token** | **97,813** | **227,578** |
| 单次行动请求平均输入 token | 约 4,277 | 约 9,273 |
| 单次行动请求最大输入 token | 5,590 | 17,178 |  

- 计入摘要生成的开销后，压缩版总 token 仍减少约 57.0%。
- 行动请求的累计输入减少约 67.3%。
- 但全部输出 token 从 5,028 增加到 5,918，因为模型额外生成了 4 次摘要。
- 压缩版的行动上下文更小；baseline 最后一次行动请求的输入已经达到 17,178 token。

压缩版总用量 = 72,713 + 3,101 + 21,999 = 97,813
无压缩总用量 = 222,550 + 5,028 = 227,578

## 结果分析与权衡

1. **总 token 用量**：计入压缩请求的输入与摘要输出后，压缩版总用量为 97,813 token，baseline 为 227,578 token，减少约 57.0%。在本次运行中，减少重复发送旧历史的收益超过了生成摘要的额外开销。虽然行动请求的输出用量下降，但计入摘要后，压缩版的累计输出 token 反而高于 baseline。

2. **上下文压缩效果**：baseline 每次行动请求的输入 token 总体随历史积累而增长；压缩版则在估算活跃上下文达到 6,000 token 阈值且存在可压缩历史时，将较旧的交互历史替换为摘要，同时保留原始 system/task 消息和最近完整的交互。其输入大小呈现增长、压缩后下降、再增长的趋势。最后一次压缩中，日志记录的估算上下文大小由 5,521 降至 2,018，减少约 63.4%；这些数字是估算值，不是 API 返回的实际用量。

3. **正确性与信息损失**：应结合两份补丁各自的独立评测结果判断任务是否成功。压缩可能遗漏重要细节，使 Agent 重复查看文件、重复测试或采取错误行动。因此，token 节省需要与任务成功率一起评价，而不能只看用量。

4. **额外开销与实验局限**：压缩版额外进行了 4 次摘要请求，消耗 21,999 token。同时，压缩版与 baseline 分别进行了 17 和 24 次行动请求，因此总用量差异也受到步数与探索路径差异的影响。模型生成具有随机性，本次结果说明压缩在这一组运行中有效降低了上下文和累计 token 用量，但不能证明它在所有运行中都会减少步骤或保持同样的节省比例。
