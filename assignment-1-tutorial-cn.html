1. 作业究竟在做什么

你不是在“写一个会修 Bug 或会下棋的模型”，而是在写模型外部的 Agent Harness（代理运行框架）。

一句话：LLM 只负责产生下一步“可能的动作”；你的 Harness 负责保存状态、提供工具、执行动作、返回环境观察，并决定何时停止。

Part 1 · 能行动

实现通用 ReAct 循环，让 CodeAgent 可以在远程终端中观察代码、运行命令、修改文件并提交 patch。

Part 2 · 能长跑

当历史过长时，把旧交互压缩成 working memory，同时保持消息协议合法和最近动作完整。

Part 3 · 能迁移

复用同一套基类循环，仅更换 prompt 与工具，把 Agent 从“修代码”迁移为“下棋”。

4. ReAct 的消息与状态数据流

OpenAI Chat Completions 接口看到的不是一个拼接字符串，而是一组有顺序的消息：

system  → 持久规则、环境说明、skill catalog
user    → 当前任务 + 初始 observation
assistant → 模型推理结果与 tool_calls
tool      → 每个 tool_call 对应的执行结果
assistant → 下一轮动作
...

必须保持的协议

  • 第一条是唯一的 system。
  • 在第一次 assistant 之前有 user。
  • 每个 tool observation 带原始 tool_call_id。
  • 一次 assistant 的多个 tool calls 都要有对应结果。
  • 文本型 assistant 回复也要保留，不能把历史弄断。

Harness 需要保存的状态

  • 原始 system/task prompt。
  • 每轮 assistant action。
  • 每个动作产生的 tool observations。
  • finished、steps_taken。
  • 压缩后的 working memory 与最近完整步骤。
理解重点：build_prompt() 是状态的“视图”；run() 是状态转换的“控制器”；execute_tool_calls() 是模型动作与真实环境之间的“适配器”。
PART 1

5. CodeAgent：建立通用 Agent Harness

Part 1 的实现结果不仅服务于代码修复，也会被 Part 3 的 ChessAgent 原样复用。

TODO 1.1.a — Agent 状态与 build_prompt

位于哪里

src/assignment/agent/base.py 的构造函数与 build_prompt()。

解决什么

LLM API 本身无记忆。Harness 必须把先前动作与观察重新放入下一次请求。

输入

system_prompt、task_prompt、历史 assistant 消息、tool observations、可选 working memory。

输出

合法的 list[dict] 消息序列，供 query_language_model() 直接提交。

你要设计的状态边界

  • 状态应该是 domain-agnostic：不能假设工具一定是 shell 或棋步。
  • 保存完整 assistant 消息，包括文本、reasoning 字段和 tool calls 中 grader 需要的结构。
  • tool result 必须紧跟并关联产生它的 assistant tool call。
  • 不要把 api_prompts/api_responses 当活跃历史；它们是审计记录。

公开测试提示：test_prompt_carries_task_action_and_result 会检查第二轮 prompt 是否仍含任务、前一动作和结果；长输出还需经过已提供的 format_tool_output() 截断。

TODO 1.1.b — CodeAgent 的 system prompt 与 task prompt

位于哪里

agent/code_agent.py::__init__。

解决什么

把通用 Agent 放进“软件工程终端任务”的语境，并告诉模型它所在的操作系统与工作目录。

输入

用户任务文本、Environment 暴露的 machine/release/system/version/cwd、skill metadata。

输出

两个字符串属性：长期规则的 system_prompt 与本次问题的 task_prompt。

  • system prompt 必须原样包含作业规定的 <system_information> JSON block。
  • 如果加载了 skills，只暴露名称与描述，不把完整正文塞进 prompt。
  • 没有 skill 时，prompt 不能泄漏 patch.txt 提交流程。
  • task prompt 应让模型知道具体 issue，而不是混入 Harness 的实现细节。
TODO 1.2 — 共享 ReAct Loop

位于哪里

agent/base.py::run()。

解决什么

持续驱动“请求动作 → 执行动作 → 记录观察”，直到领域层声明完成或预算耗尽。

输入

当前 Agent 状态、工具定义、LLM 响应、step_limit、子类 dispatcher。

输出

更新后的历史、finished 状态、trajectory 文件；超限时抛 StepLimitError。

控制流程应覆盖

  1. 在每个新动作请求前考虑 context compaction。
  2. 检查是否还允许调用模型。
  3. 调用 query_language_model() 并保存 assistant message。
  4. 如果有 tool calls，交给子类 execute_tool_calls()。
  5. 把所有 tool observations 追加到历史。
  6. 如果回复没有可解析工具，仍保留它并继续，而不是直接丢失。
  7. 无论成功、异常还是超限，都执行既有 trajectory 保存与环境 cleanup。
常见错误：在 CodeAgent.run() 和 ChessAgent.run() 分别复制循环；这会破坏本作业验证“同一个 Harness 跨领域复用”的目标。
TODO 1.3 — execute / send_message 工具执行

位于哪里

agent/code_agent.py::execute_tool_calls()，schema 在 agent/tools.py。

解决什么

把模型声明的 JSON tool call 变成远程终端动作或最终用户消息。

输入

一组 tool-call dictionaries；每项含 id、函数名、JSON 字符串 arguments。

输出

一组 role: tool 消息，每项带相同的 tool_call_id 和字符串 observation。

工具动作完成语义
execute解析 command/cwd/timeout/env/shell，并通过 Environment.execute() 运行。不结束任务；格式化 returncode、output 等结果供下一轮观察。
send_message读取 summary，作为 Agent 对用户的最终提交说明。设置 finished = True；提交后不能继续工作。
invoke_skill按名称返回已经加载的完整 SKILL.md。不结束任务；只是把更详细方法加入上下文。
  • Malformed JSON、参数类型错误、未知工具都应变成 recoverable observation。
  • 一次响应可能有多个 calls，不能只处理第一个。
  • 错误调用绝不能偷偷执行默认命令。
  • 工具输出可能很长，应使用已提供的格式化/截断逻辑。
TODO 1.4 — Skill Discovery 与 Progressive Disclosure

位于哪里

agent/base.py::load_skills()；CodeAgent prompt 与 dispatcher 使用结果。

解决什么

允许 Agent 拥有很多可复用工作流，但默认只看到小型目录，需要时再加载完整内容。

输入

一个父目录；每个直接子目录应包含一个带 YAML frontmatter 的 SKILL.md。

输出

以 frontmatter name 为 key 的 mapping；每项有精简 metadata 与完整 content。

校验职责

  • 路径存在且是目录。
  • 每个候选 skill 的 frontmatter 完整、可解析，并含必需字段。
  • skill 名称不能重复。
  • system prompt 只列 metadata，invoke_skill 才返回完整正文。
  • 仅在确有 skills 时注册 INVOKE_SKILL_TOOL。
在整个 Agent 中的位置：skill 是 prompt 与工具之间的桥梁——目录先进入 system prompt，正文再通过 tool observation 进入历史。

Part 1 的真实任务链

  1. CLI 读取 tasks/chess-terminal-move/problem_statement.md。
  2. 在 Modal testbed 的 /testbed 中启动 CodeAgent。
  3. Agent 自己复现、定位、修改和测试 chess app bug。
  4. Agent 调用 submit skill，创建并验证 patch.txt。
  5. 宿主从 sandbox 读取 patch，保存为 artifacts/fix.patch。

PART 2

6. Context Compaction：让 Agent 在长任务中保持有效记忆

压缩不是“删除旧消息”，而是把旧前缀转换为可审计的 working memory，同时保留原始指令和最近完整工具步骤。

TODO 2.1 — compact_context

位于哪里

agent/base.py::COMPACTION_SYSTEM_PROMPT 与 compact_context()。

解决什么

旧 transcript 成本不断增长，并会挤出目标、约束和最新状态。

输入

当前活跃 prompt 中可压缩的旧前缀，以及 compaction 模型 token 上限。

输出

模型生成的事实型摘要，并更新 Agent 状态，使后续 build_prompt() 变短。

Working memory 必须保留

目标、硬性约束、已查看/编辑文件、运行过的命令、具体结果、失败尝试、测试结果、阻塞点、下一步动作。

绝不能破坏

  • 原始 system 与 task 消息保持逐字不变。
  • 至少保留最近 N 个完整 assistant 步骤及其全部 tool observations。
  • 不能只留下孤立 tool 消息或丢失 tool-call 配对。
  • 不能修改 api_prompts / api_responses；它们是完整审计记录。
  • 压缩后活跃 prompt 应实质缩短，而不是把原文换个包装复制一遍。
TODO 2.2 — 在共享循环中触发 compaction

位于哪里

agent/base.py::run() 调用已提供的 maybe_compact_context()。

解决什么

压缩必须发生在“下一次模型请求之前”，否则无法降低该请求的上下文。

输入

估算 token 数、阈值、保留最近步骤数、现有 transcript。

输出

可能更新的活跃状态，以及追加到 compaction_events 的审计事件。

maybe_compact_context() 已经负责阈值判断、prompt 前后快照和事件记录；你的循环负责在正确时机调用它。

Part 2 还有一个实验交付物

对同一个 SWE-bench 实例分别运行：

  • Full context baseline：COMPACT_THRESHOLD=0。
  • Compacted：COMPACT_THRESHOLD=6000，且至少触发一次压缩。

比较两条 trajectory 的 prompt/token 使用、步骤数、压缩收益和可能的信息损失，写入 artifacts/token-usage-analysis.md。这部分考察的不只是实现，也考察你对 Agent context trade-off 的理解。

PART 3

7. ChessAgent：证明同一 Harness 可以换领域

ChessAgent 继承 Part 1/2 的循环。不同之处只在领域 prompt、工具 schema、工具执行和完成条件。

TODO 3.1.a — 定义 play_move 工具 schema

位于哪里

agent/tools.py::PLAY_MOVE_TOOL，在 ChessAgent.__init__ 注册。

解决什么

告诉模型工具叫什么、能做什么、参数必须是什么形状。

输入

无运行时输入；你定义 OpenAI function-tool JSON schema。

输出

strict schema：唯一必填字符串参数 move，使用 UCI notation，拒绝额外字段。

Schema 是模型的“动作语法”。它越明确，非法或含糊调用越少；但 schema 本身不执行棋步。

TODO 3.1.b — 执行 play_move 并维护 live state

位于哪里

chess_tools.py::_play_move() 与 chess_agent.py::execute_tool_calls()。

解决什么

把 UCI 动作发给服务器，并将 Black 自动回复后的新棋局变成下一轮 observation。

输入

HTTP client、原始 JSON arguments；dispatcher 还接收 call id。

输出

格式化棋盘状态或 <chess_error>；更新 last_state 与 finished。

  • 成功：POST /api/move，序列化返回状态，展示棋盘/FEN/历史/下一步 legal moves。
  • 失败：JSON 错误、类型错误、非法棋步、网络错误都必须可恢复。
  • 服务器会自动走 Black；Agent 永远只提交 White 的动作。
  • 一组并行调用里最多执行一个会改变棋局的 move，其余应拒绝，防止基于同一旧状态连续落子。
Observation A/B Experiment — legal moves 是否应直接提供

这不是代码 TODO，但属于评分。你要对两个模型分别运行“仅棋盘”和“棋盘 + legal moves”，共四次。

记录输入条件

模型、是否省略 legal moves、trajectory/result 文件名。

记录输出指标

play_move 总调用数、非法调用数、非法率、是否到达 game_over: true。

报告写入 artifacts/observation-experiment.md。目标不是证明某个固定结论，而是用 trajectory 证据分析工具 observation 对 Agent 行为的影响。

TODO 3.3.a / 3.3.b — simulate_move

位于哪里

Schema 在 agent/tools.py；执行在 chess_tools.py::_simulate_move()；dispatcher 在 chess_agent.py。

解决什么

让 Agent 在不改变真实棋局的情况下检查局面或试走一步，支持 lookahead。

输入

必填完整 FEN 字符串；可选 UCI move。

输出

模拟后的 JSON：fen、squares、turn、legal_moves、terminal fields；错误为 chess_error。

关键语义：它是纯查询/模拟工具，不能修改 live board，也不应改写 last_state。这与 play_move 的副作用形成清晰边界。
TODO 3.4 — run_python：Programmatic Tool Calling

位于哪里

agent/tools.py::RUN_PYTHON_TOOL、chess_tools.py::_run_python()、ChessAgent dispatcher。

解决什么

模型可以写循环、搜索或评分逻辑，并像普通函数一样调用 simulate/play，而不必手工发很多 tool calls。

输入

字符串 code、chess server port、sandbox environment。

输出

runner 的 JSON 字符串：stdout、stderr、error；随后附上重新读取的 live board。

  • 模型代码必须在 sandbox 中运行，绝不能在本地 Agent 进程 exec。
  • 代码通过 base64 传给 /opt/assignment/sandbox_python.py，避免 shell quoting 问题。
  • runner 命令非零表示基础设施失败，应包装为 chess_error。
  • snippet 内 Python exception 是一次成功启动 runner 后的用户代码错误，应留在返回 JSON 的 error 字段。
  • snippet 可能已经调用 play_move；结束后必须重读 live state，更新 finished，防止下一轮重复落子。
TODO 3.5 — ChessAgent 中的 invoke_skill

位于哪里

chess_tools.py::_invoke_skill()，注册逻辑继承自基类 skills 加载结果。

解决什么

把“如何用 Python 搜索并选择棋步”的策略按需交给模型。

输入

已加载 skills mapping 与 JSON 参数中的 skill name。

输出

指定 skill 的完整 content，或可恢复的 chess_error。

最终 trajectory 要展示工具协同：invoke_skill → run_python → 代码中 simulate_move 搜索 → 代码中 play_move 一次提交。只读 skill 后逐回合直接 play_move 不满足这一目标。

8. 测试与验收：公开测试在检查什么

当前 starter code 在非 Modal 测试中为 11 failed、4 passed、4 deselected。这正是预期起点：失败集中在学生 TODO。

测试类别可观察契约常见失败原因
Prompt history任务、assistant action、tool result 在下一步仍然存在且顺序合法。只保存字符串、不保留 tool_calls；tool_call_id 丢失。
Long output超长观察被截断，但头尾信息与省略提示仍在。绕过提供的格式化函数；把完整日志塞满 context。
Compaction旧步骤变摘要，最近完整 action/tool pair 保留，prompt 变短。摘要替换了 system/task；留下孤立 tool 消息。
Skillscatalog 只有名称/描述；invoke 后才出现完整正文。启动时暴露 skill body；frontmatter 校验不足。
Step limit预算耗尽抛 StepLimitError，同时保存日志并 cleanup。多调用一次模型；异常路径跳过 finally。
Malformed/unknown tools不执行危险动作，错误作为 observation 回给模型。json.loads 异常直接终止 run。
Chess schema/statestrict schema、POST payload、棋盘格式、last_state/finished 更新。schema 接受 extra fields；未使用原始 call id。

运行层级

快速离线

make test

先用它迭代数据结构与错误处理，不消耗 API/Modal。

环境检查

make doctor

在 billable run 前检查 submodule、Modal auth、模型 endpoint。

端到端

make run-code-agent
make check-part1

验证 Agent 真能生成可重放 patch，而非仅通过 unit tests。

10. 推荐完成顺序

下面的顺序按照依赖关系安排，避免同时调试太多层：

  1. 先建立 Agent 历史模型：构造函数状态 + build_prompt()。
  2. 再完成 CodeAgent 最小适配：system/task prompt + tools 注册。
